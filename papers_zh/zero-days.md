# 评估并缓解大语言模型发现零日漏洞（0-days）的日益增长的风险

- **分类：** Frontier Red Team（前沿红队）

Frontier Red Team（前沿红队）
2026年2月5日
 _Nicholas Carlini *、Keane Lucas*、Evyatar Ben Asher*、Newton Cheng、Hasnain Lakhani、David Forsythe 和 Kyla Guru_

[今天发布](<http://anthropic.com/news/claude-opus-4-6>)的 Claude Opus 4.6 延续了 AI 模型网络安全能力[有意义改进的轨迹](<https://www.anthropic.com/claude-opus-4-6-system-card>)。去年秋天，我们写道，我们相信我们正处于 [AI 对网络安全影响的拐点](<https://red.anthropic.com/2025/ai-for-cyber-defenders/>)——进展可能会变得非常快，现在是加速防御性 AI 使用的时刻。此后的证据只强化了这一观点。AI 模型现在能够大规模发现高严重性漏洞。我们的观点是，这是一个需要迅速行动的时刻——在窗口期仍然存在时，赋能防御者并尽可能多地保护代码。
Opus 4.6 在发现高严重性漏洞方面明显优于以前的模型，也是事情发展速度有多快的标志。安全团队多年来一直在自动化漏洞发现，在模糊测试基础设施和自定义测试装置上投入巨资，以大规模发现 bug。但早期测试中突出的，是 Opus 4.6 在没有任务特定工具、自定义脚手架或专门提示的情况下，开箱即用地发现漏洞的速度有多快。更有趣的是它_如何_发现它们。模糊测试器（fuzzers）通过向代码抛出大量随机输入来看什么会崩溃。Opus 4.6 则像人类研究人员一样阅读和推理代码——查看过去的修复以找到未解决的相关 bug，发现往往导致问题的模式，或充分理解一段逻辑以确切知道什么输入会破坏它。当我们把 Opus 4.6 对准一些测试最充分的代码库（那些有模糊测试器运行多年的项目，[积累了数百万小时的 CPU 时间](<https://google.github.io/oss-fuzz/research/llms/target_generation/>)）时，Opus 4.6 发现了高严重性漏洞，其中一些已经数十年未被检测到。
让天平向防御者倾斜的一部分意味着我们自己去做这项工作。我们现在使用 Claude 来发现并帮助修复开源软件中的漏洞。我们从开源开始，因为它无处不在——从企业系统到关键基础设施——那里的漏洞会波及整个互联网。这些项目中的许多由没有专门安全资源的小团队或志愿者维护，因此找到经人工验证的 bug 并贡献经人工审查的补丁意义重大。
到目前为止，我们已经发现并验证了 500 多个高严重性漏洞。我们已经开始报告它们，并看到我们的初步补丁落地，我们还在继续与维护者合作修补其他漏洞。在本文中，我们将介绍我们的方法，分享一些 Claude 发现的漏洞的早期示例，并讨论随着这些能力不断提高，我们为管理滥用而设置的保障措施。这只是我们努力的开始。随着这项工作规模的扩大，我们将分享更多。
## 设置
在这项工作中，我们将 Claude 放入一个"虚拟机"（字面意义上的模拟计算机）中，使其可以访问最新版本的开源项目。我们给了它标准实用程序（例如标准 coreutils 或 Python）和漏洞分析工具（例如调试器或模糊测试器），但我们没有提供任何关于如何使用这些工具的特殊说明，也没有提供会赋予它关于如何更好发现漏洞的专业知识的自定义测试装置。这意味着我们在直接测试 Claude 的"开箱即用"能力，完全依赖于这样一个事实：现代大语言模型是通用能力的智能体，已经能够推理如何最好地利用可用工具。
为了确保 Claude 没有幻觉出 bug（即发明不存在的问题，这个问题日益给开源开发者带来不适当的负担），我们在报告每个 bug 之前都进行了广泛验证。我们专注于搜索内存损坏漏洞，因为它们相对容易验证。与程序仍然可以正常运行的逻辑错误不同，内存损坏漏洞很容易通过监控程序崩溃和运行地址消毒器（address sanitizers）等工具来捕捉不崩溃的内存错误来识别。但由于并非所有导致程序崩溃的输入都是高严重性漏洞，我们随后让 Claude 批评、去重并重新优先排序剩余的崩溃。最后，对于我们第一轮发现，我们自己的安全研究人员验证了每个漏洞并手工编写了补丁。随着发现数量的增长，我们引入了外部（人类）安全研究人员来帮助验证和开发补丁。我们的意图是切实帮助人类维护者处理我们的报告，因此该流程针对减少误报进行了优化。与此同时，我们正在加快自动化补丁开发的努力，以便在发现 bug 时可靠地修复它们。
## 漏洞
以下是 Claude 发现的三个漏洞（现已由维护者修补），我们认为它们展示了 LLM 相对于其他工具的独特优势。
**GhostScript** 是一个处理 PostScript 和 PDF 文件的实用程序。Claude 在搜索漏洞时最初走了几条死胡同——既尝试模糊测试代码，又在此失败后尝试手动分析。这两种方法都没有产生任何重要发现。然而，最终 Claude 采取了不同的方法：阅读 Git 提交历史。Claude 很快发现了一个与安全相关的提交，并评论道：
    
    有一个关于 Type 1 charstrings 中"MM 混合值的堆栈边界检查"的提交。这与字体处理有关。让我获取更多关于这个提交的细节。
从这里开始，Claude 查看了代码以了解发生了什么变化：
    
    该提交显示它添加了堆栈边界检查——这表明在添加此检查之前存在一个漏洞。……如果这个提交*添加*了边界检查，那么此提交之前的代码就是易受攻击的……所以要触发该漏洞，我需要针对*此修复应用之前*的代码版本进行测试。
考虑到这一点，Claude 随后寻找调用此函数的其他位置，以发现可能未修补的类似漏洞。
    
    让我检查这些检查是否不完整，或者是否存在另一条代码路径。让我看看 gdevpsfx.c 中的另一个调用者……啊哈！这非常有趣！在 gdevpsfx.c 中，第 292 行对 gs_type1_blend 的调用没有 gstype1.c 中添加的边界检查。
做出这一观察后，Claude 迅速构建了一个概念验证崩溃（一个可以传给 GhostScript 并使其崩溃的文件），证明了它的预测。
**OpenSC** 是一个处理智能卡数据的命令行实用程序。同样，Claude 最初尝试通过模糊测试代码来发现漏洞，在此失败后，又尝试手动分析。和之前一样，当这不起作用时，Claude 采取了不同的方法：它开始在仓库中搜索经常易受攻击的函数调用。
    
    让我看看 URL 在哪里被使用——特别是 strrchr 和 strcat 操作，它们可能存在路径遍历或缓冲区溢出问题。
Claude 很快识别出一个连续使用多个 `strcat` 操作的位置。这些函数在 C 中被普遍认为不安全，因为它们允许在不对结果拼接字符串长度进行任何检查的情况下拼接字符串。因此，程序员验证输出缓冲区足够长以容纳拼接后的输入是极其重要的。对于 OpenSC，关键问题在于以下代码：
    
    char filename[PATH_MAX];  // 这个缓冲区是 4096 字节
    r = sc_get_cache_dir(card->ctx, filename,
            sizeof(filename) - strlen(fp) - 2);
    if (r != SC_SUCCESS)
            goto err;
    strcat(filename,"/");
    strcat(filename,fp);
Claude 识别出这存在缓冲区溢出漏洞。当我们查看现有模糊测试器模糊测试这行代码的频率统计时，我们看到这行代码很少被传统模糊测试器研究，因为它需要满足许多前置条件。相比之下，Claude 能够推理哪些代码片段有趣，并将其精力集中在这些地方，而不是不加区别地以同等精力研究所有代码行。
**CGIF** 是一个处理 GIF 文件的库。在这个案例中，让我们惊讶的不是 Claude 如何_发现_这个 bug，而是它如何_验证_这个 bug 并产生一个证明漏洞真实存在的概念验证。
简而言之，Claude 发现这个库假设压缩数据总是会比其原始大小更小（这通常是一个安全假设），而这个假设可以被利用。它做到这一点的方式很有挑战性。GIF 文件格式使用 LZW 压缩算法压缩数据。与更传统的、以（距离，长度）对编码匹配的基于 LZ77 的压缩器不同，LZW 构建一个常用词元对的字典（要么是单个字符，要么是词元对）。然后，当压缩器第二次遇到这个词元时，它可以输出一个较短的比特串，表示"再次输出这个词元"。（对于那些熟悉语言建模的人来说，LZW 在精神上与 BPE 分词的过程非常相似。）
CGIF 隐式地假设压缩字符串的压缩大小总是小于未压缩大小——这几乎总是成立的。然而，Claude 立即识别出这里的漏洞：
    
    要触发溢出，我们需要：
    
    • 小的 numPixel（小图像）
    • 写入许多 LZW 代码
    
    产生最多 LZW 代码的模式是：
    
    • 不发生压缩（每个像素变成一个代码）
    • 发生多次重置
    
    使用 4 色调色板（索引 0-3）：
    
    • initDictLen = 4
    • 字典在 MAX_DICT_LEN (4096) 个条目后填满
    • 当字典达到 4096 时发生重置
    
    要用小图像触发溢出：
    
    • numPixel = N
    • 缓冲区大小 = (N + 2) 个代码
    • 我们需要生成 > N + 1 个代码
    
    每个像素可以生成 1 个代码 + 重置。
    
    但可能产生更多代码的模式是当我们有长度为 1 的序列时。
也就是说，Claude 认识到 LZW 维护一个固定大小的符号表；如果有可能使符号表的大小达到上限，那么 LZW 会在数据流中插入一个特殊的新"清除（clear）"词元。这导致输出的"压缩"大小超过未压缩大小——触发缓冲区溢出漏洞。
这个漏洞特别有趣，因为触发它需要对 LZW 算法及其与 GIF 文件格式的关系有概念性的理解。传统模糊测试器（甚至覆盖率引导的模糊测试器）很难触发这种性质的漏洞，因为它们需要做出特定的分支选择。事实上，即使 CGIF 具有 100% 的行覆盖率和分支覆盖率，这个漏洞仍然可能未被发现：它需要一系列非常特定的操作。
## 保障措施
伴随 Claude Opus 4.6 的发布，我们引入了一层新的检测，以支持我们的保障团队[识别和响应](<https://www.anthropic.com/news/detecting-countering-misuse-aug-2025>)对 Claude 的网络滥用。这项工作的核心是[探针（probes）](<https://alignment.anthropic.com/2025/cheap-monitors/>)，它测量模型在生成回应时的内部激活，使我们能够大规模检测特定危害。通过这次发布，我们创建了新的网络特定探针，以更好地追踪和理解 Claude 在网络安全领域可能的滥用。
在执行方面，我们正在发展我们的管线，以跟上这种新的检测架构。这包括更新我们的网络执行工作流以利用基于探针的检测，以及扩大我们应对网络滥用所采取的行动范围。特别是，我们可能会实施实时干预，包括阻止我们检测为恶意的流量。这将给合法研究和一些防御性工作带来摩擦，我们希望在问题出现时与安全研究社区合作寻找解决方法。我们致力于通过努力使 Claude 既安全又有效，保持其在网络安全领域的前沿地位。
总之，这些变化代表我们在防止滥用能力方面向前迈出的有意义的一步：不仅在于我们能检测到什么，还在于我们能多快、多有效地对发现采取行动。
## 结论
Claude Opus 4.6 能够在测试充分的代码库中发现有意义的零日漏洞，即使没有专门的脚手架。我们的结果表明，语言模型可以在现有发现工具之上增加真正的价值。我们上面描述的保障工作对于管理这带来的双重用途风险至关重要。
展望未来，我们和更广泛的安全社区都将需要面对一个令人不安的现实：语言模型已经能够识别新颖的漏洞，并且可能很快超过即使是专家级人类研究人员的速度和规模。
与此同时，现有的披露规范将需要演进。行业标准的 90 天窗口期可能无法应对 LLM 发现 bug 的速度和数量，行业将需要能够跟上节奏的工作流。
这是一项正在进行的工作，我们很快会分享更多——包括我们正在了解的这些能力如何演进，以及安全社区如何最好地利用它们。
