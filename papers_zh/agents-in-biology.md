作者：Laura Luebbert。基于 Ferdous Nasri、Sarah Gurev、Patrick Varilly、Krithik Ramesh、Nuala A. O'Leary、Jonah Cool、Bernhard Y. Renard、Pardis Sabeti 和 Laura Luebbert 的[研究](<https://arxiv.org/pdf/2606.06749>)。  

_在这篇文章中，Laura Luebbert 主张我们需要让生物数据基础设施对智能体更加友好。作为案例研究，她和她的团队让科学研究智能体（Claude、Biomni 开源版（Biomni OSS）¹、Edison Analysis²、GPT）从 NCBI Virus——病毒学家用于监测和诊断检测开发等任务的数据库——检索序列数据。即使是最强的模型也没有始终如一地达到可靠数据集构建所需的准确度。但一旦她和团队加入了 gget virus——一个确定性检索层——准确度就上升到接近 100%。对科学智能体而言，更广泛的教训是：确定性检索工具（目前）对让智能体工作流程更可靠至关重要，而生物数据库将需要以智能体作为规模化用户来设计。_

_用 AI 智能体在生物数据基础设施中穿行，就像开车穿过一座为汽车时代之前设计的古城：基础设施可能很美，甚至很周到，但满是狭窄蜿蜒的街道，现代车辆难以通行（特殊的文件格式、分散的数据库和一次性的检索脚本）。³ 你可以用交通标志、停车场和偶尔拓宽的道路来改造这座城市，但基本布局仍然难以通行，因为它当初是为另一种出行方式设计的。相比之下，软件基础设施基本上就是为汽车（智能体）的需求而造的：铺好的道路、清晰的车道、标准化的信号，以及为从头到尾快速行驶而设计的系统（版本控制、文档完善的 API 和包管理器）。_
_因此，编码智能体的进展比生物智能体快得多。软件通常提供结构化的数字工作流和可靠的接口，而计算生物学中用于数据检索和验证的基础设施往往是脆弱的、异构的和依赖流程的。我们用于在其中导航的工具必然是为特定领域或假说量身定制和调校的。此外，软件提供可测试的输出，可以快速编译和验证（例如，通过生成一个通过项目测试的补丁来解决 GitHub issue），而生物学很少提供简单、可验证却有意义的回报。_
_因此，生物智能体的瓶颈不仅在于推理，还在于缺乏广泛的确定性执行层来查询生物数据。科学家可以表达他们的意图（例如，找出所有具有该结构域的人类激酶并提取它们的结构），但智能体往往缺乏访问包含所需信息的数据库的可靠方式。_
_在生物和科学工作流程中，即使是小错误也可能造成严重后果。例如，从错误的基因组版本中检索坐标，就可能使下游的生物学解释失效。无意中混用 RefSeq 和 GenBank 记录、把部分基因组当作完整基因组、混淆分段病毒的片段名称，或因元数据字段不一致而遗漏相关记录，也是如此。研究之美与挑战在于，细节往往至关重要。_
_就像开车穿过一座意大利山城：如果街道太窄、弯道太急、路线依赖当地知识，那么车再强大也没用。如果我们想让智能体帮助科学发现——从疫情应对到药物设计再到生物建模——我们就需要构建它们能像人类一样可靠导航的生物数据基础设施。_

### **Karpathy 关于 Web 开发的演讲告诉了我们什么：用 AI 智能体做生物学  
**

智能体需求与人类构建工具之间的这种不匹配并非生物学独有。只要把智能体插入到专为人类使用而设计的环境中，就会出现同样的摩擦。
几个月前，Andrej Karpathy 做了一个关于 AI 时代软件的[演讲](<https://www.youtube.com/watch?v=LCEmiRjPEtQ>)，最后抱怨了一件听起来太熟悉的事情。他用 vibe-coding 做了一款小型 Web 应用，但当他试图把它变成真正可用的产品（身份验证、支付、部署）时，他在浏览器仪表板里点击折腾了一周。
正如他所总结的：「代码是最容易的部分！大部分工作都在浏览器里，点来点去。」文档一直告诉他「去这个 URL，点这个下拉菜单」。他的结论是，没有人应该做这种事。相反，我们必须为智能体而构建。
Karpathy 在软件智能体世界中经历了某种新事物，而生物学研究者已经与之斗争了很久：试图让智能系统在围绕异构信息、隐含约定和人类点击浏览器的环境中运行所带来的痛苦。
## **案例研究：病毒学中的「点击税」  
**

早在 AI 智能体出现之前，计算生物学家和遗传学家就已经开始为传统计算生物学制造工具，逐渐蚕食这个问题。Biopython、BioPerl、BioJulia、Entrez Direct、BioMart、gget 等软件包以及许多其他工作流库，都是在努力把生物数据从浏览器界面搬到研究者可以直接在其上进行计算的地方。
问题在于，生物数据并不存在于一个具有单一接口的单一数据库中。它是一个混乱的道路网络，每条路都有自己的标识符、约定、格式、过滤逻辑和程序化访问程度。有些数据很容易以程序化方式访问。另一些则不那么容易。
病毒学尤其属于较难的情况之一。从疫苗和诊断检测设计到为蛋白质模型构建训练数据，研究工作流往往始于从 NCBI Virus 检索序列。NCBI Virus 是 GenBank、RefSeq 以及包括 Pathoplexus 在内的国际 INSDC 生态系统中的病毒序列记录集合，背后是一个可搜索的 Web 界面。作为病毒暴发监测构建工具的研究者，我们深知这些检索背后隐藏着多少专家知识。在病毒学实验室里，NCBI Virus 的数据集整理说明往往以长长的复杂过滤器列表形式传阅，用户必须在 Web 界面中手动复现这些过滤器：这正是 Karpathy 抱怨的那种浏览器点击工作流。
当前刚果民主共和国由本迪布焦病毒（Bundibugyo virus）引起的埃博拉病暴发，就是一个鲜明的例子，说明简化的病毒数据访问可能带来真实世界生死攸关的后果。2026 年 5 月 14 日，刚果民主共和国金沙萨国家生物医学研究所（INRB）分析了 13 份血样，次日确认其中八份为本迪布焦病毒病，⁴ 随后宣布暴发埃博拉疫情。到 5 月 29 日，WHO 已报告刚果民主共和国境内超过 1,000 例确诊和疑似病例，包括 200 多例死亡。研究人员还生成了首批近乎完整的暴发基因组，帮助确认这次暴发是由一次新的溢出事件引起的。
这些基因组给公共卫生官员带来了三个紧迫的问题。首先，这次暴发的病毒与此前见过的埃博拉病毒有多大不同？其次，现有的诊断方法还能检测到它吗？第三，现有的疗法还能保护人们免受其害吗？回答这些问题需要将新基因组与通过 NCBI Virus 和 Pathoplexus（与 NCBI Virus 同步）获得的埃博拉历史基因组进行比较。但这一步并非轻易可自动化：分析的初始步骤涉及手动点击 Web 界面、手工复现复杂过滤器，并寄希望于最终数据集完整且正确。
这个工作流难以自动化的原因是，NCBI Virus 的很多过滤逻辑只存在于这个 Web 界面中。这对人类来说很烦人，对智能体来说则是灾难性的。如果研究者想要 2025 年发布的所有含表面糖蛋白的 SARS-CoV-2 序列，一位经验丰富的病毒学家在浏览器里点几下可能就行。但以程序化方式，可能需要一个数百行的脚本，把多个 API（REST、Datasets、E-utilities）粘合起来，逐页检索结果、核对标识符、下载数百 GB 的数据，结果在本地过滤后大部分都要丢弃。
即使某个资源有 API，由于各种原因，智能体也可能难以可靠使用——例如 API 没有暴露与 Web 界面相同的过滤语义、元数据字段文档不全或标准化不一致、标识符跨来源变化，或者「正确答案」依赖于专家人类知晓而机器只能推断的约定。
### **当智能体无论如何都要尝试时会发生什么  
**
为了更好地理解把智能体与数据库连接起来的挑战，我们开发了一个测试，检验最先进的科学研究智能体（Claude、Biomni OSS、Edison Analysis、GPT）在被要求使用现有基础设施从 NCBI Virus 检索病毒序列时有多能干。我们的基准 VirBench 包含 120 个现实的病毒序列查询，覆盖 40 种病原体，并配有经人工验证的基准真值计数。这些查询反映了病毒监测、诊断检测设计和蛋白质模型训练数据构建中出现的任务。例如，一个查询要求智能体「从 NCBI 检索 TaxID 3052462（扎伊尔正埃博拉病毒（ZEBOV））的病毒序列，须满足以下标准：宿主生物：人类，样本采集地理位置：非洲，采集日期在 2014 年 1 月 1 日或之后、2014 年 6 月 20 日或之前，最短序列长度：15,200 个碱基，最多 1,900 个模糊字符（N），排除实验室传代样本。」
当智能体被放手自行解决这些查询时，各系统之间的性能差异很大，而且更新的前沿模型有实质性的改进。然而，即使是最强的模型也没有始终如一地达到可靠数据集构建所需的准确度和可重复性。Claude Sonnet 4、Claude Opus 4.7、Biomni OSS、Edison Analysis、GPT-5.2-pro 和 GPT-5.5 的平均准确度从 16.9% 到 91.3% 不等。对于这些数据检索任务，门槛实际上是 100%：在某些情况下，一条缺失或错误的记录可能决定一个诊断检测是否看起来覆盖了流行中的病毒多样性，或决定一次暴发被推断为比实际早几周还是晚几周开始。此外，同一个模型在被问同一个问题三次时，常常给出差异很大的答案，破坏了可靠科学工作流程所需的准确度和可重复性。对于上面那个埃博拉病毒示例查询，Sonnet 4⁶ 一次运行返回了 106 条序列（预期：266 条），第二次返回 15 条，第三次返回 5 条，尽管每次收到的提示词完全相同。
诸如此类的不一致会给下游分析带来后果。我们用上面展示的查询检索埃博拉病毒序列并构建系统发育树——这是重建暴发期间病毒样本亲缘关系的标准分析。我们能从系统发育树中获得的一个重要量是到最近共同祖先的估计时间（TMRCA）。这是推断出的暴发根日期，它可以改变关于病毒起源时间和地点以及病毒循环了多久的结论。在本例中，从人工整理的 NCBI Virus 序列集构建的树恢复了 2014 年 1 月的 TMRCA，与 2014 年埃博拉病毒暴发的[先前报告](<https://www.science.org/doi/epdf/10.1126/science.1259657>)（95% 最高后验密度区间为 1 月 27 日至 3 月 14 日）一致。相比之下，Sonnet 4 检索到的三个序列集中的两个明显不完整，其中一棵树把推断的 TMRCA 推回到了 1922 年。剩下的数据集（运行 1）表面上看似乎合理，但没有检索到几内亚的序列，并把估计的 TMRCA 移到了 2014 年 4 月，改变了推断的暴发时间。
![展示扎伊尔埃博拉病毒系统发育树的图表](assets/agents-in-biology/img_001.img)使用 [Delphy](<https://www.biorxiv.org/content/10.1101/2025.03.25.645253>) 推断的 2014 年西非疫情扎伊尔埃博拉病毒系统发育树。末端按采样国家着色；灰色表示缺失或错误检索的国家元数据。红色虚线标记每棵树到最近共同祖先的估计时间（TMRCA）。左上方的树由通过 NCBI Web 界面手动检索的序列构建，而运行 1–3 由 Sonnet 4 智能体使用网络搜索和代码执行工具组装的序列集生成。分析与可视化：Gage Moreno。
NCBI Virus 检索尝试之间的变异性也会影响关于疗法的结论。我们检索了埃博拉病毒糖蛋白序列，以检查 maftivimab 和 MBP134 所结合的表位——这两种抗体疗法是针对扎伊尔埃博拉病毒开发的，也是当前埃博拉病毒暴发中的 [WHO 优先治疗候选药物](<https://www.who.int/news/item/28-05-2026-experts-convened-by-who-advise-on-candidate-treatments-and-vaccines-for-ebola-disease-caused-by-bundibugyo-virus>)。我们询问，在相关的扎伊尔埃博拉病毒序列中，这些抗体靶向的区域以前是否出现过突变。这类分析可以让研究者了解，随着病毒进化，一种疗法是否还能继续保护患者。如果底层序列不完整或被错误获取，就可能推翻他们的结论。在我们的示例中，Sonnet 4 检索的序列在第一次尝试时接近通过手动 NCBI 查询获得的结果。在重复运行时，它遗漏了大部分突变残基。而在第三次运行时，它突出了另一组不同的残基，对这些靶区域的变异性产生了三种不同的印象。⁷
![现存扎伊尔埃博拉病毒突变的图示](assets/agents-in-biology/img_002.img)扎伊尔埃博拉病毒糖蛋白上的现存突变以红色显示，颜色越深表示突变频率越高。球体表示抗体疗法 maftivimab 和 MBP134 的已知足迹。最左边的可视化由人工整理的 NCBI 数据集构建，而运行 1–3 由 Sonnet 4 智能体使用网络搜索和代码执行工具组装的序列集生成。所示的 PDB 结构为 7TN9。分析与可视化：Sarah Gurev。
这两个例子都说明了科学中的一个更广泛模式：看起来只是微小检索选择的细节，却可能改变生物学结论。在本例中，病毒序列检索中不一致的模型性能以及失败模式的性质表明，大部分变异可归因于基础设施的缺陷。当智能体未能检索大型结果集时，它们会少计数；当过滤器应用错误时，它们会多计数。例如，与预期计数偏差最大的是可用记录数量庞大的病毒，包括甲型流感、HIV-1 和 SARS-CoV-2——在这些病毒上，检索中途停止和不正确的下游过滤会严重扭曲最终数据集。它们还在其含义取决于上下文、约定或信息恰好存储位置的元数据字段上遇到困难。随着查询变得更加复杂——尤其是超过三四个同时过滤器时——性能逐渐下降。
归根结底，智能体往往对任务理解得足够好，足以尝试执行，但它们缺乏一种机器可执行的方式来完成任务、验证任务并重复任务。由此产生的答案可能看起来合理，而实际上却是错误的，这尤其危险，因为序列检索通常是更长的生物学工作流的第一步。
### **用于病毒数据检索的确定性层  
**

 _关于 VirBench 和 gget virus 的更详细说明，请阅读[预印本](<https://arxiv.org/pdf/2606.06749>)。_
为了把病毒数据检索变成智能体和人类可以直接调用的东西，我们与 NCBI 的研究人员合作开发了 _gget virus_。起初，这看起来可能只是连接正确 API 调用那么简单。实际上要难得多：NCBI Virus 是多个底层资源的门户，包括在美国、欧洲和日本维护的国际同步序列数据库，因此回答一个看似简单的查询往往需要拼合来自多个地方的信息。
为了复现 NCBI Virus Web 界面的行为，_gget virus_ 必须协调其下的不同系统，包括 REST、Datasets 和 E-utilities API。_gget virus_ 决定哪些过滤器可以通过这些现有 API 应用，哪些必须在本地检查，因为 Web 界面暴露的过滤行为无法从单一程序化端点获得。它处理批量检索，使大型结果集（如 SARS-CoV-2 和甲型流感数据集）被完整检索，而不是被任意截断。当过滤依赖于存储在单独数据库中的附加信息（例如指示序列是否包含特定病毒蛋白的 GenBank 记录）时，_gget virus_ 会检索这些记录，用它们来应用过滤器，并在最终输出中保留相关的 GenBank 信息。然后它返回人和机器都可读的标准化输出，并附有详细日志，显示最终结果是如何产生的。⁸
![展示 AI 智能体在有和没有 gget virus 时在 VirBench 基准上表现的图表](assets/agents-in-biology/img_003.img)AI 智能体在有和没有 _gget virus_ 时在 VirBench 基准上的表现。VirBench 评估智能体正确检索病毒序列数据集的能力。最后一根柱状图显示 _gget virus_ 直接运行、不经智能体的结果。图改编自 Nasri 等人，2026。
当我们让智能体访问 _gget virus_ 后，所有智能体的准确度都上升到 90% 以上，GPT-5.5 达到 99.7% 的峰值。运行间的变异性基本被消除，模型之间的性能差距急剧缩小。换言之，**增加一个确定性检索层让模型选择变得不那么重要了**。这一点尤其重要，因为可靠的数据集构建不应依赖于能否访问最新或最昂贵的模型，也不应依赖于知道哪个模型对给定数据库效果最好。相反，更便宜的模型加上正确的工具可以减少变异性并实现更广泛的访问。
_gget virus_ 通过把一个复杂的、基于浏览器的检索工作流转变成一个准确且可重复的接口，使现有智能体在病毒数据检索上更加可靠。回到我们那个可步行城市的类比：这就像我们在人行基础设施下面加了一条高速公路隧道，配有上下匝道、畅通的互通立交，以及通往已知里程碑的出口编号。
### **正如 Karpathy 所说：「让[基因组数据]对智能体可访问」**
我们希望模型在生成假说、设计实验或推理机制时富有创造力。但创造力之下的那一层——基因标识符、模式、检索逻辑、坐标系统、元数据约定和数据访问路径——必须无聊地可靠（或者换句话说，确定性的）。_gget virus_ 是构建这些_上下文引擎_的更广泛努力中的一个例子：为生物数据构建可靠、智能体可访问的基础设施。其他努力正在从 AI-for-science（面向科学的 AI）系统中涌现，其中许多依赖把智能体连接到生物数据源的模型连接框架（harness），包括 ToolUniverse、Edison Scientific 的 Robin、Biomni 以及相关的生物医学智能体。挑战在于弄清楚这种确定性应该放在哪里，以及如何构建它。
当我们考虑到模型能力变化之快时，连接器和连接框架的工作就变得更加棘手。如果我们把上面的结果沿模型曲线向前延伸，很容易想象一个（非常近的）未来，像 _gget virus_ 这样的工具的收益趋近于零：智能体变得足够好，能自行穿越混乱的门户、核对标识符、正确分页并从失败中恢复。在那个世界里，连接框架可能不再需要。尽管如此，即使智能体能做到，也不意味着这项任务应该每次都由智能体处理（并重新发明）。一个能艰难穿过混乱生物信息学工作流的模型，对于常规科学工作来说可能仍然太贵、太慢、太难审计或太难信任。而且，如果智能体最终让今天的连接框架过时，对生物数据库的教训依然成立：在考虑我们的用户时，我们需要把智能体也考虑进去，我们需要为规模而构建。
