## **主要发现**
  * 在[先前](<https://www.anthropic.com/research/measuring-agent-autonomy>)[工作](<https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic>)的基础上，我们引入了一个研究交互式智能体编程的框架，它基于对 2025 年 10 月至 2026 年 4 月间约 40 万个 Claude Code 会话的[隐私保护分析](<https://www.anthropic.com/research/clio>)。我们评估了任务构成、人机协作和成功率。
  * 在典型会话中，人做出大部分规划决策（做什么），而 Claude 做出大部分执行决策（怎么做）。一个人带入会话的领域专业知识越多，Claude 每条指令完成的工作就越多。在编码任务上，每个主要职业的成功率——以通过测试或提交的工作等可验证证据来完成其人设想的任务——平均都与软件工程师几乎持平。
  * 一个人拥有的领域专业知识越多，会话以成功告终的频率就越高——尽管中级用户与专家用户之间的差距不大。在我们观察的七个月里，用于调试的会话占比下降了近一半，使用转向了更多端到端的智能体式用途：部署和运行代码、分析数据以及撰写非代码文档。
  * 在这七个月里，典型任务的价值（我们通过与自由职业招聘信息的比较来估算）在几乎每一种工作中都有所上升——平均约上升 25%。

## **引言**
智能体编程已经起飞。自 2025 年底以来，有编码智能体活动的 GitHub 项目占比已翻了一倍多，¹ 而 Claude Code 用户现在平均每周花 20 小时使用该工具。² 没有正式编码经验的人能否成功引导智能体完成复杂的技术工作？这些工具的快速普及和改进对广泛的知识工作意味着什么？虽然我们尚未完全回答这些问题，但我们从 Claude Code 的使用数据中寻找早期信号。
本报告基于对 2025 年 10 月至 2026 年 4 月间约 23.5 万人约 40 万个交互式会话的[隐私保护分析](<https://www.anthropic.com/research/clio>)，提供关于 Claude Code 在实践中如何被使用的证据。它建立在先前聚焦于 Claude Code 会话中[自主性度量](<https://www.anthropic.com/research/measuring-agent-autonomy>)以及[Claude Code 如何改变 Anthropic 的工作方式](<https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic>)的研究基础之上。³ 在这里，我们引入一个描述交互式 AI 编码助手使用情况的框架：正在做什么样的工作、谁在做、是否成功。我们聚焦于通过命令行界面（CLI）、[Claude.ai](<http://claude.ai/redirect/website.v1.885f58b9-7bdd-416a-89ac-4517a9d2f952>)或 Claude Code 桌面应用进行的 Claude Code 使用。⁴ 通过追踪智能体编程使用如何随模型能力提升而变化，我们可以更好地理解这些工具如何影响编码专业人员与知识工作者的劳动力市场。
Claude Code 上发生的事情，可能是知识工作未来走向的预览——随着智能体嵌入非编码工作。我们发现 Claude 正在处理更复杂、更有价值的任务。与此同时，智能体编程中仍然存在明确的分工：人决定构建什么，智能体决定如何构建。
我们还看到证据表明，放大工具有效使用效果的是领域专业知识，而非编码熟练度。具体来说，领域专家成功得更频繁，也更容易从错误和误解中恢复。然而，专家与中级用户之间的差距不大——这表明在一个领域达到熟练水平，就足以几乎像那些拥有精深造诣的人一样有效地使用该工具。
这些发现让我们对劳动力市场可能的转变有了早期解读。在我们的数据中，成功取决于一个人对其试图解决问题的理解程度，而非他们是否受过编码训练。如果这些模式在整个经济中成立，那就表明：虽然智能体编程工具可能在吸收一些实现密集型工作，但它们也在回报那些对工作中要解决的问题有扎实理解的人。编码智能体并没有取代领域专业知识——工人带给智能体的理解越多，智能体能够完成的高质量工作就越多。
##   
**分工**
### **人们用 Claude Code 做什么**
为了理解人们用 Claude Code 做什么，我们将每个会话归类为九种工作模式之一——即最能描述该会话试图达成目标的单一活动。⁵ 四种模式直接涉及编写或维护代码：_构建_新东西、_修复_损坏的东西、_测试_代码，以及_编排_其他智能体或自动化流水线。另一个类别是_运维_软件——部署、配置、运行流水线、监控系统。还有两类更多是弄清楚要做什么：_理解_现有系统如何工作，以及在动手之前_规划_变更。还有两类采取的行动与代码无关，或代码对最终产品只是附带性的：_分析_数据和通过演示文稿及其他散文式文档_沟通_。
约 56% 的会话由编写（25%）、修复（26%）或测试与编排代码（5%）构成。软件运维占 17%，14% 的会话是规划或探索，13% 产生分析或散文式产出（图 1）。
![](assets/claude-code-expertise/img_001.img)**图 1：九种工作模式  
**每个交互式会话被归类为最能描述其试图达成目标的单一模式。  

  
我们通过让一个模型读取每个会话的转录本进行分类，然后使用我们的隐私保护分析工具，将会话与每次会话自动记录的遥测数据（包括是否有任何代码行被添加或删除）进行核对。两个来源具有高度一致性——例如，被我们的分类器标记为创建或修改代码的会话中，超过 90% 在遥测数据中显示了代码变更。详见[附录](<https://cdn.sanity.io/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf>)。
### **谁决定什么**
Claude Code 有多自主？能力评估表明上限很高且在不断上升：在 [METR 的时间跨度评估](<https://metr.org/time-horizons/>)等基准上，前沿模型现在可以完成需要人类数小时的软件任务，并自主克服途中的障碍。但实际使用情况究竟如何？在这里，我们考察真实会话中人和 Claude 各自做了多少引导。
我们从两个角度研究这个问题。首先，我们关注人们在多大程度上把_决策_托付给 Claude；其次，我们考察他们交给 Claude 多少_行动_。为了理解会话中的决策分工，我们构建了一个基于会话内容的隐私保护决策归属分类器。我们让分类器列出会话中所有有意义的决策。我们将这些决策分为规划（做什么、采取哪种方法、什么算完成）和执行（改哪些文件、写什么代码、用什么语言写、运行哪些命令）。然后分类器将每个决策归属给 Claude 或用户，从而给每个会话两个数字：用户的规划决策占比和用户的执行决策占比。
平均而言，人们做出约 70% 的规划决策，但只做出约 20% 的执行决策（图 2）。在实践中，智能体编程存在明确的分工——人决定构建什么，智能体决定如何构建。
为了理解会话中行动的委托情况，我们考察会话的结构而非内容。一个 Claude Code 会话涉及 Claude 与用户来回交换提示词（来自用户）和行动（由 Claude 执行）——用户写一条提示词，Claude 去执行一些工作，然后用户再写一条提示词，如此反复。在典型会话中，大约有四轮这样的交流。在我们 10 月到 4 月的历史数据中，用户发送的每条提示词平均会触发 Claude 执行约 10 个行动——有时超过 100 个。⁶ 在每一轮中，Claude 读取文件、编辑代码、运行命令，平均写出 2,400 字的输出。
Claude 在两次检查点之间做多少工作，很大程度上取决于谁在做决策。当用户保持对执行的控制（即做出超过 80% 的执行决策）时，Claude 每轮采取的行动较少（约 8 个行动）。而当 Claude 接管规划（即做出超过 80% 的规划决策）时，它承担的行动最多（约 16 个）。
![](assets/claude-code-expertise/img_002.img)**图 2：Claude 在规划和执行决策中的占比  
**各会话中，归属给 Claude 而非用户的规划决策（做什么）和执行决策（怎么做）占比的分布。在典型会话中，用户做出约 70% 的规划决策，而 Claude 做出约 80% 的执行决策。  
  

### 专业水平
Claude 根据每份转录本，以从新手到专家的五分制来评定用户在任务上的表观专业水平。专业水平分类器寻找三个信号：用户如何精确地表述其指令、他们让 Claude 验证什么，以及是用户倾向于纠正 Claude 还是 Claude 倾向于纠正用户。请注意，专业水平捕捉的东西与职位或一般能力截然不同，而且关键是，它是_针对具体任务_的。一位资深工程师问第一个 Rust 问题是 Rust 的新手。一位从未用过 Python 的会计师，如果能准确告诉 Claude 一个 Python 脚本必须执行哪些对账规则，并抓住它在月末结账时处理错的边缘情况，那么她就是该任务的专家。
下表显示了我们如何在分类器中定义每个专业水平，以及来自编码智能体会话公开数据集 [SWE-chat](<https://huggingface.co/datasets/SALT-NLP/SWE-chat>) 的示例请求。被归类为新手的对话给出泛泛的指令，不暗示任何领域特定知识。专家级对话则传达出对代码库和技术环境的深刻理解。
![](assets/claude-code-expertise/img_003.img)**表 1：专业水平分类器  
**示例是对我们分类器标记的真实会话的转述、匿名化和浓缩。表中使用的许多会话来自编码智能体会话的公开数据集 [SWE-chat](<https://huggingface.co/datasets/SALT-NLP/SWE-chat>)。  

  
我们量化了专业水平与 Claude 每条提示词的输出和活动之间的关系。在典型的新手会话中，每条提示词触发约 5 个 Claude 行动和约 600 字输出，而专家会话触发的行动链长度是前者的两倍多（12 个行动），携带五倍的输出（3,200 字）（图 3）。新手与专家会话之间的这种差距出现在每一种工作和每一个任务价值区间内。
这些度量补充了我们在[上一份关于 Claude Code 的报告](<https://www.anthropic.com/research/measuring-agent-autonomy>)中的自主性度量——后者追踪智能体运行了多久、人们多频繁自动批准其行动。相比之下，我们的决策归属度量捕捉的是在整个会话中谁做出了实质性决策，而我们的每条提示词输出和行动度量则衡量每个人类提示词触发了 Claude 多少自主活动。

**对于更有经验的用户，Claude 每条提示词产生更多行动（左柱）和更多文本输出（右柱）。箱体跨越四分位距（以中位数分割）。须线表示第 5 至第 95 百分位。白点表示几何均值。两个上升趋势均具有统计显著性（p < 0.001），每个相邻级别之间的台阶也同样显著，并且在控制工作模式、任务价值、月份、职业和模型系列的回归中（每个专业水平 +9% 行动和 +13% 输出）仍然显著，标准误按用户聚类。  

## **谁在使用 Claude Code，用于什么**
### **用户**
为了理解是谁在做这些工作，我们从会话转录本推断每个用户的职业，将其映射到劳工统计局标准职业分类（SOC）体系中的 23 个主要组之一。分类器被指示只依赖以下信号：智能体会话开始时加载的项目上下文、用户文件的名称和结构、他们引用的任何产物（如法律文件、临床数据、财务报告、课程大纲等）以及他们使用的词汇。⁷ 它被明确指示_不要_把编码行为本身当作编码职业的证据。只有当有明确信号表明软件或数据工作是用户的职业时，会话才被归类为编码 SOC 代码（计算机和数学职业）。一个律师构建脚本来自动标记合同文件夹中缺失条款的会话，会被映射到法律职业，即使该会话的工作主要是软件。当没有任何关于用户职业的信号时，会话保持未分类。
我们能够在约 70% 的会话中推断出职业。在这部分中，涵盖大多数软件相关工作类别的计算机和数学职业毫不意外是最大的群体。其次是商业和金融运营；艺术、设计、媒体；管理；以及生命、物理和社会科学。我们样本中增长最快的非软件职业群体是管理、销售和法律职业。
### **工作**
2025 年 10 月至 2026 年 4 月间，用 Claude Code 完成的工作构成发生了实质性变化。最明显的变化是，用于修复损坏代码的会话占比从 33% 下降到 19%（图 4）。取而代之的是，我们看到围绕代码的工作占比增加。软件运维从会话的 14% 增长到 21%。编写和数据分析大约翻倍，从约 10% 增长到会话的约 20%。
任务本身也变得更加有价值。我们通过询问这项工作在自由职业市场上的报价来近似每次会话的经济价值，并以真实招聘信息的公开数据集进行校准。按此衡量，平均会话的估计价值在 10 月到 4 月间上升了 27%。这一上升在多种工作中都成立。构建、运维和修复类任务的价值都增长了约三分之一或更多（分别约 43%、34% 和 32%）。这些价格估计是粗略的，因此我们主要用它们来比较任务之间的相对价值，而不是按字面解读为美元金额。⁸ 关于任务估计器的构建细节，见[附录](<https://cdn.sanity.io/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf>)。
![](assets/claude-code-expertise/img_005.img)**图 4：Claude Code 工作的构成与价值，2025 年 10 月至 2026 年 4 月  
**七个月窗口内各工作模式中的会话占比。修复损坏代码的会话占比从 33% 降至 19%，而软件运维、数据分析和文档撰写有所增长。  
  

## **成功取决于用户带来了什么**
任务的估计价值是了解 Claude Code 如何帮助人们完成工作的一种方式。另一个角度是看有多少会话是成功的，以及会话的哪些特征与成功相关。在我们所有的成功度量中，我们都看到一个清晰的模式：一个人在会话中表现出的专业水平越高，成功的可能性就越大。大部分增益集中在专业水平量表的下端——新手会话与中级会话之间的差距大于中级与专家之间的差距。
在转向成功会话的特征之前，我们应该明确我们如何衡量成功。我们无法观察到用户的真实世界结果，也无法直接问他们是否从 Claude 那里得到了想要的东西。相反，我们依赖两个互补的基于转录本的度量。第一个是_判定成功_，来自一个读取完整转录本并判定该人是否成功完成了其设想目标的分类器（选项：成功、部分成功、失败、无明确目标）。两个配套分类器随后对支持该判定的证据强度进行评级，以确定_已验证成功_。一个成功信号分类器寻找成功的可验证证据。具体来说，它寻找与工作匹配的 git 活动，如提交和拉取请求，以及测试套件通过和用户的明确肯定。它将会话从「无信号」到「弱信号」（1）再到「多个硬信号」（5）进行评分。一个平行的失败信号对事情出错的证据进行评分——错误、失败的测试、重试、用户对输出提出异议。已验证成功要求_同时满足_会话被判定为成功，并且至少有一个硬性的可验证成功信号。对于下面聚焦于会话成功或失败程度的分析，我们排除了被分类为「无明确目标」的会话，它们约占我们完整样本的 7.7%。
## **专业知识的回报**
那么什么样的会话最成功？事实证明，上文描述的会话专业水平评级对会话的成功至关重要。
人们可能会担心专业水平并不是真正的驱动因素——也许专家只是选择不同的任务，或在其他方面有差异。在本节中，我们通过比较做同类工作、估计价值相同、月份相同、主题相同、来自同一大致职业群体的会话，来部分解决这一担忧，并询问结果如何随该人的评定专业水平而变化。
![](assets/claude-code-expertise/img_006.img)**表 2：从分类器导出的成功与失败定义  
**示例转述并概括了来自智能体编码交互公开数据集 [SWE-chat](<https://huggingface.co/datasets/SALT-NLP/SWE-chat>) 的真实会话，并由我们的分类器标记。
在我们所有的成功度量中，一个人在会话中表现出的专业水平越高，会话成功的可能性越大。被评定为新手的会话，达到我们最严格的度量_已验证成功_的比例为 15%，至少部分成功的比例为 77%。被评定为中级或以上的会话，达到已验证成功的比例为 28–33%，部分成功的比例为 91–92%（图 5）。
在每项度量中，大部分增益来自从新手到中级；从中级到专家之间，斜率减小。在[附录](<https://cdn.sanity.io/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf>)中，我们给出了图 5 背后回归的细节。
![](assets/claude-code-expertise/img_007.img)**图 5：专业水平与会话如何结束  
**按用户在任务上的评定专业水平（从新手到专家的五分制）划分的会话结果。左面板包含所有会话。中间和右面板限于遇到麻烦（失败信号 > 3）的会话，并显示仍然以各种成功和失败定义告终的占比。每个点都是一个调整后的比率——我们通过只比较具有相同工作模式、相同任务价值区间、相同月份、相同任务主题和相同用户类型（软件相关职业或否）的会话，来估计专业水平之间的差异。这些点背后回归的细节在附录中。须线是样本均值的置信区间（大多数太小，在此图中不可见）。这些图排除了被成功结果分类器判定为无明确目标的会话。  
  

在遇到挑战的会话中也出现了类似的梯度。当失败信号记录到已验证的失败证据时，我们说会话_遇到麻烦_。这可能是一个错误、一次失败的测试、多次尝试做同一件事，或用户表达沮丧或不满。在遇到麻烦的会话中，已验证成功的占比从新手评定会话的 4% 上升到专家评定会话的 15%，并考虑了上述所有控制变量（图 5）。从更宽松的度量来看，我们发现至少部分成功的占比对于新手为 60%，对于中级到专家会话为 80–81%。
我们还追踪反向关系——专业水平与各种失败度量。请注意，在此分析中，被判定为失败的会话是那些甚至没有部分成功的会话。我们说一个遇到麻烦的会话如果被判定为失败_且_写入了零行代码，就是_被放弃_的：用户看似新手的会话有 19% 以放弃告终，而其他所有人的比例为 5–7%。换言之，经验最少的用户在难以得到想要的结果时更可能放弃。专业知识的部分价值似乎在于能够把智能体引向正确的方向。⁹
### **  
职业可能不如专业水平重要**
软件相关职业的人在约 30% 的会话中总体上达到已验证成功，而其他职业的用户约 26% 的时间达到已验证成功。在产生代码的会话（即添加或修改至少一行代码的会话）中，这两个数字分别为 34% 和 29%（图 6）。在更宽松的成功定义下，软件相关职业与其他职业之间的差距缩小——两个群体在产生代码的会话中分别有 89% 和 88% 的时间达到至少部分成功。那五点的差距很小，而且在七个月里既没有扩大也没有缩小，尽管两个群体的成功率都在提高。在产生代码的会话中，我们数据集中十大职业中的每一个，其成功率都落在软件工程师的七个百分点以内。管理职业在已验证成功上最高，略高于软件工程职业。其较高的已验证成功率可能反映了可迁移到指挥智能体的管理技能。但也可能部分反映我们的度量方式：验证部分依赖于转录本中的明确确认，而管理者在得到所要求的东西时可能更倾向于明确沟通。¹⁰
  

![](assets/claude-code-expertise/img_008.img)**图 6：按推断职业划分的编码会话中已验证成功和判定成功率  
**在添加或更改至少一行代码的会话中，按用户推断的职业群体划分，达到严格成功定义（判定成功和已验证成功）的会话占比，针对最大的十个群体。每个群体都在软件/数学用户（SOC 代码：计算机和数学职业）的七个百分点以内。误差条是按不同账户计算的 95% 置信区间。  
  

## **展望**
本报告的结果描绘了一幅新兴图景：智能体编程如何放大某些形式的知识和技能，同时替代其他形式。在产生代码的会话中，每个主要职业的成功率都落在软件相关职业的几点以内。看来编码智能体正在使编码背景对成功编程变得不那么重要。
与此同时，成功的会话更可能展现领域专业知识。被评定为专家的会话达到已验证成功的频率是新手的两倍多，而当会话遇到麻烦时，新手放弃会话的比率是其他人的数倍。协作的形态为这幅图景增添了更多色彩——领域专家能够引导 Claude 用每条指令做更多工作。因此，引导 Claude 走向成功的能力更多来自对领域的掌握，而非编写代码的能力。拥有这种掌握的人——无论在哪一领域——现在或许能够完成他们以前无法完成的技术工作。没有任何这类专业知识的人，从同样的工具中获得的收益要少得多。而且增益主要来自胜任而非精通——对领域有可用的掌握就能获得大部分收益，而深度专业化只在其上再添一点点。
这些发现是初步的。与我们的多数研究一样，我们无法衡量真实世界的结果，例如会话中编写的代码事后是否真正被使用或弃用，或者它是否产生了有经济价值的产物。此外，本报告排除的非交互式使用占活动的重要份额。开发一个衡量它的框架是未来工作的优先事项。我们所有对会话的分类都依赖模型对转录本的阅读。在[附录](<https://cdn.sanity.io/files/4zrzovbb/website/a94728142a45694292336165947f8d6e3e1a357e.pdf>)中，我们展示分类器在预期方向上与独立遥测数据一致，并在大多数会话上与一个强参考模型一致。但分类器在大规模上的验证仍然具有挑战性，而 Claude Code 会话又增加了难度，因为它们可能过长、过于复杂，人类标注难以作为基准真值。
本报告中的图景将随着模型、用户以及它们之间分工的变化而更新。我们希望这些度量能让我们在重大转变发生时追踪它们。例如，如果专业知识的回报开始随时间下降，那将表明模型开始提供用户目前带来的基本判断，而这些工具的收益正扩大到领域专家之外。如果软件职业之外的用户成功完成的编码会话占比继续增长，那可能表明软件生产正成为各领域普通工作的一部分，而非单一职业的产物。这些转变将改变谁从智能体编程中受益、受益多少，并将对劳动力市场中最受珍视的东西产生影响。
