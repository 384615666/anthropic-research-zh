在 Anthropic，编写代码已不再是构建系统或开展研究的瓶颈。Claude 能够自主迭代研究循环、对复杂程序做微观优化，并以前所未有的速度与规模从零搭建新服务。如今的瓶颈，是所有按人类尺度构建的开发者基础设施：源代码控制、构建与 CI。
2026 年 5 月，Anthropic 平均每天合入约 2,500 项代码改动；到 9 月，我们每天合入超过 30,000 项。我们预计这一增速短期内不会放缓：合入代码的潜在需求近乎无限，而每消除一个瓶颈，都会立刻让我们产出的代码量再涨一截。
![](assets/redesigning-source-control/img_001.webp)
2026 年 1 月至 9 月，每天合入我们单体仓库的改动数量。
为支撑这一增长，我们构建了内部版本控制系统 Scion，并在五个月内把单体仓库从 git 完整迁移过来。同一时期，我们还构建并上线了代码评审界面（名为 Antique）、代码搜索、一套功能丰富的源代码控制 IAM 系统，以及管理和落地大量已评审代码的新方法等等。本文将专门聚焦我们如何构建 Scion。这是个有意思的案例研究：Claude 写代码的能力，既是一开始把我们推入这一处境的原因，_也是_ 我们得以迅速构建出高质量、可扩展系统来应对它的手段。
### 单体仓库的膨胀
在探讨我们构建了什么之前，得先说明我们的工作负载有多不寻常。不出所料，Anthropic 用 Claude 写软件的程度远超几乎任何一家公司，因此我们往往最先看到按人类尺度打造的工具在哪里开始吃紧。源代码控制只是其中一例。虽然我们不认为很多组织会在极短期内遇到这些问题，但我们猜想，用不了多久，其他使用 AI 编程工具的公司也会撞上同样的压力点——这正是我们想分享所做与所学的原因。
git 是一个去中心化系统：每个克隆都是完整、自包含的仓库，能在完全离线的情况下计算 diff、查看历史与 blame、检出任意版本。对绝大多数仓库来说，这是正确的设计，也是 git 成为标准的重要原因。
随着单体仓库膨胀，它越来越不符合这一设计空间。光是主分支的历史就接近 100 GB，而一份 _压缩后_ 的工作副本超过 25 GB。我们每天为 CI 执行约 2,500 万次代码检出，这还没算开发者环境、智能体沙箱与研究作业。若按朴素方式拉取，那将意味着每天超过 600 PB 的 git 流量。
git 提供了只处理仓库局部的工具，例如浅克隆、稀疏检出与 promisor remote。除此之外，大型单体仓库还有一些标准变通办法，比如内部 git 镜像，以及保存在 blob 存储里的仓库快照（seed）。这些我们都用过——高峰期我们运维着数百个内部 git 镜像来应对负载。这为我们争取了时间，但随着合入速率上升，它们越来越难运维。两次刷新之间，seed 会离 main 的尖端越来越远；而要让 diff、blame 这类依赖历史的操作在部分克隆上正常工作，也越来越费心。
![](assets/redesigning-source-control/img_002.webp)
扩展 git 检出规模的典型配置。
退一步看，我们注意到，和大多数公司一样，我们把 git 当成只有一个权威副本的中心化系统来用，但我们的客户端几乎全是生来就在线的智能体与作业。那些让 git 在分布式、离线场景下表现出色的特性，恰恰在仓库变大时损害了我们扩展的能力。于是我们自问：如果从一开始就以「智能体永远在线」为前提来设计源代码控制，它会是什么样子？
### 面向智能体尺度的源代码控制原则
随着智能体编程兴起，关于软件开发方式的许多常见假设都在变化。构建 Scion 时我们拥抱了这些变化，因此得以在若干核心原则上采取与 git 根本不同的思路。超大型单体仓库的源代码控制已有先例，尤其是 Google 的 [Piper](<https://en.wikipedia.org/wiki/Piper_\(source_control_system\)>) 与 Meta 的 [Sapling](<https://sapling-scm.com/>)，2 因此我们能把它们来之不易的经验融入 Scion 的构建。我们的原则是：
**客户端永远在线。** git 假定客户端离线工作、需要仓库的完整副本。由于我们的客户端几乎全是智能体与作业，我们围绕一台始终可达的服务器来设计 Scion 的客户端与协议，让客户端按需取数据。
**客户端与服务器不对称。** 在 git 里，每个客户端都能充当完整的服务器。在 Scion 里，服务器负责回答关于文件历史与 blame 的查询、创建提交、执行合并与变基等等。客户端只维护一个有界的本地对象缓存、把工作副本文件铺到磁盘上、监听文件系统变化，并为用户提供一种顺手的与服务器协作的方式。它自身几乎算不了什么，但作为交换，本地所需的数据也少得多。
**一套完备的源代码控制服务能支撑许多新颖应用。** 在 git 里，某个 CI 作业或工具若想查询仓库（例如某行最后是谁改的、两次提交如何关联），就得维护一份仓库本地副本，或指望厂商专属 API 给出答案。在 Scion 里，客户端用到的所有源代码控制查询也通过 API 暴露出来，因此很多时候作业根本不需要本地仓库。我们的许多内部工具——比如自动 bisect 与回滚流水线——若没有这种廉价、可编程的源代码控制访问，根本无法规模化落地。
**一切都必须可水平扩展。** 高峰期我们跑着数百个 git 镜像，这极大地挤占了容量；一旦仓库超出镜像的磁盘或内存上限，就再也扩不动了。在 Scion 里，仓库数据是分布式的，每个组件都能独立扩展；任何地方（连服务器上也）都不存在仓库的完整物化副本。它也没有 packfile（git 把对象压缩打包的产物）的对应物，因此无需做仓库维护。
**提交必须廉价、增量且无锁。** 在 git 里，你在本地提交，再 push 出去共享工作。在 Scion 里，每次提交、变基或合并都发生在服务器上，因此没有东西需要 push，但每一项操作都必须够快。创建一次提交并更新其下游数据结构的成本，必须随改动大小而非仓库整体大小增长，否则服务器跟不上。Scion 的开发生命周期不鼓励使用 ref（指向提交的指针，例如分支与标签），只保留 main ref 或发布分支——因为每台服务器都得达成一致的 _全局_ 状态，是个迫在眉睫的扩展难题。
**工作副本是可选的，且生来就是稀疏的。** 由于我们的单体仓库如此庞大，又每天为 CI 检出代码数千万次，我们希望尽可能避免检出。有了 Scion，比如某个 CI 作业需要一次提交与其合并基之间的 diff，可以直接向服务器索取。写入同理：许多写入负载也能跳过检出，完全通过 API 完成。Scion 的协议以稀疏检出（只包含客户端所请求的目录）与虚拟化检出（按需物化文件）为核心，因此当作业确实需要磁盘上的文件时，客户端只需为它真正读到的内容付费。
### Scion 如何工作
理解这些原则在构建 Scion 时如何落到实地会很有帮助。这些洞见也适用于其他源代码控制系统，或更宽泛地说，适用于软件开发生命周期的其他阶段。
#### 数据结构
在 Scion 里，工作单元是「变更集」（changeset），即预写日志中的一条记录。变更集存放着你对 git 提交所期望的大部分信息。但 git 提交存的是指向树的指针，变更集存的则是一份相对其第一父节点发生变化的文件列表，1 以及指向 blob 存储中压缩文件内容的内容寻址指针。变更集在服务器端创建，立刻就能在所有地方访问。
![](assets/redesigning-source-control/img_003.webp)
Scion 中变更集的结构。
这一结构让我们能以极高吞吐接收变更集，因为既没有要接收的 packfile，也没有加锁或跨服务器协调，更没有需要挪动的 ref。Scion 技术上确实支持 ref，但由于创建与拉取提交都不涉及它，移动一个 ref 只是对单条 Spanner 行做一次比较并交换（compare-and-swap），与创建变更集彼此分开。
变更集只记录改了什么，因此单靠它无法快速回答「某行最后是谁改的」「哪些提交动过某文件」这类问题。为此，Scion 从变更集中构建出额外的数据结构，包括专用于文件 blame 与路径历史的结构，以及提交图的跳表。我们把不直接属于变更集的一切称为「派生数据」，并通过一套通用机制统一计算。每一类派生数据都以递归方式定义：某个变更集上的取值，由它各父节点上的取值算出。
这套机制有三个好处。第一，当某种新数据结构能让某项操作更快时，我们可以轻松新增一类派生数据。第二，对每一类，我们都能选择立即计算还是延后处理，从而避免物化用不到的数据。第三，由于客户端永远看不到这些数据结构的内部，我们可以在不改动客户端的前提下优化它们。随着系统成长，我们多次新增过派生数据类型，例如用于复制检测或基于路径的文件搜索的新索引。
#### 扩展 Scion
一小队 Scion 服务器为客户端所需的任何操作提供源代码控制 API，例如获取变更集、计算 diff、查找合并基、拉取 blob。所有源代码控制数据都是内容寻址的，因此一份数据一旦写入就不再改变，任何服务器都能缓存它而无需与其他服务器核对。结果是，这些服务器可水平扩展、几乎不需要协调。它们本质上是大型缓存，同时还能即时计算派生数据，并把结果写回 Spanner。
Scion 的众多使用方不再需要各自维护本地仓库。对那些需要查询源代码控制、尤其是提交祖先关系与 blame 的 CI 作业或工具来说，拉取并维护仓库过去是一项沉重的运维负担。迁移早期，在我们还没有自己的客户端、仓库格式与协议之前，Scion 只回答这类「元数据」查询。拉取文件内容与物化工作副本的数据密集程度高得多，需要单独设计。
Scion 的 scn 客户端在几个重要方面偏离了 git 的拉取协议，因而天然适合一种高度可扩展、且比 git 服务器省得多 CPU 的架构。Scion 的协商不会告诉服务器客户端已有什么，而只围绕客户端想要的树与 blob 展开。从根树出发，客户端在本地存储里查缺，递归请求缺少的树，再对 blob 重复这一过程。每个请求针对的都是永不改变的特定对象，因此任何缓存都能应答，整个架构很像传统的分层缓存。这一过程还高效且可续传，因为不存在单个数 GB 的 packfile 响应。稀疏检出乃至虚拟化检出都无需特别支持——客户端干脆不请求它不想要的树。
在集群里，客户端通过套接字与一个守护进程 scion-daemon 通信，后者为整台节点存放对象。我们的大多数节点都需要访问单体仓库，而同一节点上的作业复用的往往是同一批对象。每个守护进程从一份定期刷新的快照起步，随后只与本区域的树与 blob 缓存服务器（称为 scion-cache）对话。这些缓存服务器直接从内存、以守护进程将要消费的磁盘格式流式送出对象，因此不必花时间计算客户端缺哪些对象或做增量压缩。当某个缓存缺对象时，它去向权威的 scion-servers 索取，后者按需从 Spanner 或云存储读取。
scion-daemon、scion-cache 与 scion-server 对这一协议响应的是完全相同的 RPC，因此客户端无需知道缓存拓扑。理论上任一层都能与任意其他层通信，但我们严格执行分层，以隔离故障域。我们要避免这样的局面：某个区域的 scion-cache 一出故障，就压垮上游 scion-servers，进而拖垮整个系统。
![](assets/redesigning-source-control/img_004.webp)
Scion 的检出架构。
这套系统的每一层都保持 99% 以上的缓存命中率，且不需要长期存活的状态，因此要扩容很容易。就 CPU 与内存需求而言，我们如今的 Scion 基础设施占用比此前的 git 镜像基础设施小 200 倍。CI 与研究作业检出代码快了两个数量级（以秒计而非以分计），这为整个集群腾出了可观的容量；光是 CI 就实现了 25% 的 CPU 容量收益。客户端与缓存都不必做仓库维护，这简化了我们作业的生命周期管理。
### 构建 Scion 的收获
我们动手构建 Scion，大约与 [Claude Mythos Preview](<https://www.anthropic.com/claude/mythos>) 和 [Claude Tag](<https://www.anthropic.com/news/introducing-claude-tag>) 在内部可用的时间重合。这两个版本同时放大了对 Scion 的需求，也切实加快了我们构建它的速度。
这里有个格外突出的例子。那年早些时候，我们基本靠手写完成了 git 到 Scion 的摄取流水线第一版，作为原型。我们本以为它不错——直到拿到 Claude Mythos Preview 的早期内部快照。我们请它把整段重写一遍，在没有给出任何进一步指示的情况下，它交出的版本内存消耗少了 20 倍、速度快了 4 倍，同时完整保留了摄取顺序与数据结构周围所有隐含的不变量。
![](assets/redesigning-source-control/img_005.webp)
2026 年 1 月至 9 月，每周合入 Scion 与 Antique 代码库的改动。
构建并运维 Scion 的所学，为「面向智能体尺度的软件该怎样构建」提供了一些有意思的启示。
**小团队的快速开发会变得更常见。** 一个七人团队既构建了 Scion，_也_ 构建了 Antique（我们的代码评审工具，单为它就能再写一整篇博客），此外还做了六七个相关系统，并在五个月内完成全面迁移。而这一切，是在每天合入的代码量增长 10 倍的同时做到的。过去，开发并部署这样一套源代码控制系统，往往要一家公司耗费数年迭代迁移、投入多得多工程师。我们认为，这种快速、灵巧的迁移未来会更常见。
**工程师的价值不减，但工作正在变化。** 参与这套系统的所有工程师如今都会认为 Claude _写_ 代码比自己更强。但我们的工程师仍然提供了对高层系统间组件与设计层取舍的宝贵理解，围绕「想解决哪些问题」「需要达到怎样的规模」做出有依据的选择。我们常常发现，工程师的角色是对 Claude 说「不」。智能体有时会为满足某个本就不该被允许的模式，而违背系统的核心约束。这在我们的迁移里尤其常见。例如，有好几个系统不去问我们的代码评审工具，而是靠线性读提交日志来暴力查某次改动何时合入 main。Anthropic 也大量使用对抗式评审，它在很多方面极其有效，却也可能目光短浅，因此需要熟练的工程师把 Claude 从「因假想顾虑而过度设计系统某些部分」的倾向里拉回来。比如，有一次评审对信任另一个内部服务过分戒备，结果让 Claude 加上了过量的校验与复杂度。我们的团队成员至今仍审阅系统的每一次变更请求，但他们现在审的是改动的 _意图_，而不是逐行读代码。
**我们得以大幅提升优化与质量。** 凭 Claude 能以远快于我们的速度写出海量代码，Scion 成了我们经手过测试最充分、防护最严密的代码库之一。即便时间线很紧，我们仍为我们遇到过的每一个非平凡的基础设施与源代码控制交互构建了封闭仿真，还做了模糊测试与精细的限流。Claude 还随手找到了不少重要优化——例如某次祖先查询漏用了我们一个索引的算法级优化，这类事本要专家花上数天乃至数周去分析调优……而它第二天又照样来了一遍。
![](assets/redesigning-source-control/img_006.webp)
在原生 Scion 仓库上观测到的性能提升。
**我们为新形式的单体仓库安全打下了基础。** 在庞大的单体仓库里，管理安全、保密与合规，与管理其体量和规模同样重要。我们从一开始就带着这些考量构建 Scion。它支持对仓库做细粒度访问控制，也能把权限施加到单个目录，从而在不丢掉单体仓库好处的前提下保护最敏感的代码。此外，我们构建的代码评审工具能表达关于审批的复杂语义约束，让我们把「仅改注释」这类简单变更与敏感的逻辑变更区分开来，使人类评审者能聚焦在最要紧的改动上。
**运维水准可以迈上新台阶。** 我们团队大量使用 Claude Tag，它帮我们监控系统的每个组件。例如，我们建了一些 Slack 频道，让 Claude 一门心思盯住某一个组件的健康状况。我们管这些 Claude 叫「超级粉丝」（superfans）。我们有 scion-daemon 超级粉丝、scion-cache 超级粉丝、Antique 合并队列超级粉丝等等。它们能访问我们的遥测与日志，表现得像一位经验丰富的工程师——除了刷新图表、留意任何异常之外没别的事可做。我们也为所有系统配了传统告警，但超级粉丝能察觉细微而新颖的问题，相形之下那些告警倒显得单薄了。
**我们正在彻底重审既有成见。** 这个项目促使我们非常严肃地重新审视其他按人类尺度设计的工作流。比如，一套规规矩矩的合并队列，在智能体尺度下就没多大意义。当成百上千项改动能在测试跑着的同时合入时，CI 究竟还意味着什么？我们没能有效复刻「在合并队列上加全局仓库锁」这一行业标准，于是转而投入合并后、部署前的自动化测试。这确实意味着并发改动可能冲突，但 Claude 解决这些冲突，通常比人类甚至还没识别出它们来得更快。
### 为更广阔的生态做贡献
我们把 Scion 看作「能力日益增强的 AI 智能体所带来的扩展顾虑」的答案之一。分享这些细节，是想给团队如何应对类似挑战提供一个例子，并不指望我们的方案或考量适合每一种情形。
就通用用途而言，Scion 绝不适合取代 git。这里勾勒的这些概念，其实只对真正庞大的单体仓库才有意义——要么有数万名工程师，要么有成群的智能体在大量写代码。况且 Anthropic 很特殊：我们为内部用途消耗 token 的能力，远超任何一家企业现实上愿意花的量。我们这么做，既为满足自身的软件开发需要，也为检验 Claude 的能力。
实际上，很难把 Scion 做成一种对其他组织广泛有用的形态。它与 git 差异太大，意味着公司得迁移开发生命周期的每一个环节，而且它需要自带的代码评审、代码搜索与 CI。这些组件的内部版本高度定制，其他组织难以采用；我们也担心，硬要做一个试图取悦所有人的公开版本，到头来并不会太有用。
不过，我们预计这类问题在未来六到十二个月会变得更普遍，而让每一家用 git 的公司都独自面对类似挑战，是对工程资源的低效使用。有鉴于此，我们认为能做的最有影响力的事，是分享我们的思路，让其他开发者把 Scion 中最成功的部分应用到 git 上，而不必脱离整体模型。git 服务器不必与 git 客户端以同样方式工作；已经存在一些能带来显著扩展改进的新颖服务器架构。git 平台可以提供像 Scion 那样完备的服务器端 RPC，甚至以跨 forge 的标准化方式提供，让 git 客户端学会与之对话。协商协议也不必非得长成今天这个样子，git 里各种稀疏与浅层特性同样可以组合得很好。
最后，我们要致意：git 社区花了近二十年，把这个平台扩展到服务数百万开发者。我们的贡献要窄得多：分享我们对「智能体式软件开发如何与这些系统相互作用」的早期观察，以便与 GitHub、GitLab 及开源社区携手，支撑开发者不断变化的需求。当软件开发生命周期与 AI 的指数曲线交汇时，我们都在同一条船上。
